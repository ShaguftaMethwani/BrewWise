# Project Problem Statement: BrewWise — An AI-Powered Personalised Pour-Over Coffee Assistant

## 1. Project Overview

Build **BrewWise**, an AI-powered coffee brewing assistant that helps users discover the optimal pour-over brewing recipe for their coffee beans by simply taking a photograph of the coffee bag.

Specialty coffee bags contain valuable information about the beans, including the coffee estate, origin, varietal, processing method, roast level, roast date, tasting notes, altitude, and sometimes recommended brewing parameters. However, translating this information into an effective brewing recipe requires coffee knowledge, experimentation, and an understanding of how different brewing equipment affects extraction.

Coffee enthusiasts often search multiple websites, brewing communities, blogs, Reddit discussions, and coffee forums to find recipes for specific beans. When no recipe exists for a particular coffee, they must experiment with grind size, water temperature, coffee-to-water ratio, and pouring technique themselves.

BrewWise aims to simplify this process through a combination of computer vision, optical character recognition (OCR), retrieval-augmented generation (RAG), and AI-powered recipe recommendation.

The application should allow a user to photograph a coffee bag, automatically extract the relevant coffee characteristics, search for existing brewing recipes for the same or similar beans, and generate a personalised pour-over recipe based on the available evidence and the user's equipment.

The system must distinguish between recipes retrieved from real sources and recipes generated by the AI. It must not fabricate existing recipes, sources, or claims of community consensus.

## 2. Problem Statement

Design and implement an intelligent coffee brewing application that converts unstructured information printed on coffee packaging into actionable, evidence-informed brewing instructions.

The system must solve the following problems:

1. **Coffee information extraction:** Identify and extract coffee characteristics from an image of a coffee bag, even when the text is distributed across different sections, printed in small fonts, or mixed with branding and illustrations.

2. **Recipe discovery:** Search available online resources and a curated knowledge base for pour-over recipes associated with the exact coffee, its estate, producer, processing method, or other relevant characteristics.

3. **Evidence-based recipe recommendation:** Retrieve relevant recipes using RAG, evaluate their relevance to the identified coffee, and present suitable recipes with their original sources.

4. **Personalised brewing:** Adapt recommended recipes to the user's grinder, dripper, filter, dose, and preferred brewing style when that information is available.

5. **Recipe generation when evidence is unavailable:** If no sufficiently relevant recipe can be found, generate a practical starting recipe based on coffee characteristics, brewing principles, available equipment, and clearly stated assumptions.

6. **Transparency and explainability:** Explain why a recipe was selected or generated, identify which information came from the coffee bag or external sources, and distinguish verified facts from AI-generated recommendations.

The ultimate goal is to help coffee enthusiasts go from a photograph of a coffee bag to a reproducible, personalised brewing recipe with minimal manual research.

## 3. Target Users

- Specialty coffee enthusiasts who brew coffee at home.
- Beginners who want good results without understanding every brewing variable.
- Experienced home brewers who want to discover recipes from other coffee enthusiasts.
- Users who own different grinders and pour-over drippers and need equipment-specific recommendations.

## 4. Core User Journey

### Step 1: Photograph the coffee bag

The user opens the application and uploads or captures a photograph of a coffee bag.

The system analyses the image and extracts available information, such as:

- Coffee brand and producer.
- Estate, farm, washing station, or cooperative.
- Country and region of origin.
- Coffee varietal.
- Processing method, such as washed, natural, honey, or anaerobic.
- Roast level and roast date.
- Tasting notes.
- Altitude.
- Any roaster-provided brewing recommendations.
- Other relevant information printed on the packaging.

The system should recognise that not all bags contain every field and that terminology varies across roasters.

The extraction process must preserve uncertainty. If a field is missing, illegible, or ambiguous, it should be marked as unknown rather than guessed.

### Step 2: Review the extracted information

Display the extracted information in an editable coffee profile.

Allow the user to correct OCR mistakes before searching for recipes.

For example:

- Brand: Blue Tokai
- Estate: Riverdale Estate
- Region: Chikmagalur, India
- Process: Washed
- Roast: Light
- Varietal: Unknown
- Tasting notes: Citrus, florals, stone fruit

These values are illustrative and should not be hardcoded into the application.

The system should also identify which fields were explicitly read from the bag and which were inferred or obtained from an external source.

### Step 3: Configure brewing equipment (optional)

Allow users to select or enter their brewing equipment.

**Grinder**
- Brand and model.
- Grinder type: hand grinder or electric grinder.
- Burr type, if known.
- Optional grind setting or adjustment range.

**Dripper**
- Brand and model.
- Dripper type, such as V60, Kalita Wave, Origami, April, flat-bottom dripper, or another supported device.
- Dripper size.
- Filter type, if relevant.

**Additional optional preferences**
- Preferred coffee dose.
- Desired beverage strength.
- Brewing experience: beginner or experienced.
- Preferred brewing time.
- Available water temperature range.
- Whether the user prefers a simple recipe or a more experimental technique.

Equipment selection must remain optional. Users who skip this step should still receive a useful default recipe.

The application should support extensible equipment catalogues instead of restricting the system to a small, hardcoded list.

### Step 4: Search for existing recipes

Search the application's recipe knowledge base for recipes that match the identified coffee.

Use a retrieval-augmented generation pipeline to find relevant recipes and supporting information.

Search relevance should consider multiple levels of specificity:

1. Exact match: the same coffee from the same producer or estate.
2. Strong match: the same coffee release or lot, including alternative naming conventions.
3. Related match: the same producer, estate, varietal, or processing method.
4. Analogous match: coffees with similar roast levels, processing methods, density or origin characteristics, where sufficient data is available.
5. General brewing knowledge: relevant guidance for the selected dripper and equipment.

Exact matches should receive the highest priority.

The system must not treat a recipe for another coffee from the same estate as an exact match. It must explain when it is using a related coffee as a reference.

Search results should include, where available:

- Recipe title.
- Author or source.
- URL.
- Coffee identification.
- Grinder and dripper used.
- Coffee dose and water quantity.
- Grind size.
- Water temperature.
- Pouring sequence.
- Total brew time.
- Extraction or tasting observations.
- Publication date, if available.
- Retrieval relevance and the reason for the match.

When multiple relevant recipes are available, compare them and identify meaningful similarities and differences.

### Step 5: Evaluate the retrieved evidence

Do not blindly pass retrieved documents to an LLM and ask it to generate a recipe.

Implement a retrieval evaluation stage that assesses:

- Whether the document actually contains a brewing recipe.
- Whether the coffee identity matches the target coffee.
- Whether the brewing method is pour-over.
- Whether the recipe is sufficiently complete to be actionable.
- Whether the source is accessible and identifiable.
- Whether the recipe is compatible with the user's equipment.
- Whether important brewing parameters conflict with other retrieved recipes.

The system should distinguish between the following outcomes:

**Outcome A — Exact or highly relevant recipes found**

Present the strongest matching recipes, preserving the source attribution and original brewing parameters. Explain any adaptations made for the user's equipment.

**Outcome B — Related recipes found**

Present recipes for related coffees and clearly label them as references rather than recipes verified for the exact coffee. Use them as evidence when formulating a recommendation.

**Outcome C — Insufficient evidence found**

Generate a new starting recipe using general brewing principles and available coffee characteristics. Explain that no sufficiently relevant recipe was found in the searchable sources.

A lack of results must never be presented as proof that nobody has published a recipe online.

### Step 6: Generate a personalised brewing recipe

Generate a pour-over recipe using the extracted coffee profile, retrieved evidence, equipment details, and user preferences.

The recommended recipe should contain:

- Brewing method and dripper.
- Coffee dose in grams.
- Total water quantity in grams.
- Coffee-to-water ratio.
- Water temperature in °C.
- Grind size expressed in a format appropriate to the selected grinder, where supported.
- Filter preparation instructions, where relevant.
- Bloom duration and water quantity.
- Number of pours.
- Water quantity and timing for each pour.
- Pouring style, such as centre pours, circular pours, or pulse pouring.
- Target total brew time.
- Step-by-step brewing instructions.
- Expected flavour profile, clearly labelled as a prediction rather than a guarantee.
- Troubleshooting suggestions for sourness, bitterness, weak flavour, or slow drawdown.

All numerical parameters must be internally consistent.

For example, a 15 g dose at a 1:16 ratio requires 240 g of total brewing water. The water quantities across all pouring stages, including the bloom, must add up to the stated total.

The recipe should not pretend to know a grinder-specific setting when that setting is unsupported or unavailable. Instead, provide a relative grind recommendation and explain how to adjust it based on the result.

If retrieved recipes provide a useful starting point, prioritise them over unsupported speculation. If a recipe is generated independently, identify it as an AI-generated recommendation.

### Step 7: Explain the recommendation

Provide a concise explanation of why the recipe was recommended.

For example:

- The coffee is labelled as light roast, so the recipe starts with a relatively high water temperature.
- The washed processing method informs the initial brewing hypothesis but does not determine a single correct recipe.
- The selected dripper tends to have particular flow characteristics, which influence the pouring strategy.
- A recipe from a related coffee provides a starting point, but its parameters have been adapted to the user's equipment.

These explanations should be grounded in the available information. Do not claim that every coffee of a particular process, origin, or roast level must be brewed in one specific way.

### Step 8: Support iterative brewing

After brewing, let the user record feedback.

Ask for information such as:

- Was the coffee too sour, too bitter, too weak, too strong, or balanced?
- Was the drawdown faster or slower than expected?
- Did the coffee taste different from the expected flavour profile?
- What grind setting and brewing time did the user actually use?

Use this feedback to suggest targeted adjustments.

For example:
- Excessive sourness may justify a controlled increase in extraction.
- Excessive bitterness may justify a controlled decrease in extraction.
- A very slow drawdown may justify examining grind size, pouring agitation, filter choice, or clogging.

Recommendations should account for the fact that flavour diagnosis is not always one-to-one. Change one or two variables at a time where practical.

Allow users to save recipes, revisit previous brews, and compare different brewing attempts for the same coffee.

## 5. Functional Requirements

### FR-1: Image input and OCR

- Accept photographs from a camera or uploaded image files.
- Detect text and extract structured coffee metadata.
- Handle missing, ambiguous, and unreadable information.
- Support manual correction of extracted fields.
- Retain the original image only as required by the application's privacy and storage design.
- Separate observed text from externally enriched information.

### FR-2: Coffee identity resolution

- Normalise coffee names, estate names, producers, and processing terminology.
- Handle alternative spellings, abbreviations, and naming variations.
- Avoid incorrectly merging distinct coffee lots or releases.
- Track confidence in identity resolution.
- Request clarification when ambiguity materially affects recipe retrieval.

### FR-3: Recipe data acquisition

Implement a modular ingestion system for gathering recipe data from permitted sources.

Potential sources include:
- Publicly accessible coffee blogs and brewing guides.
- Public forum discussions and community posts, where access is permitted.
- Curated recipes contributed by users.
- Existing structured recipe datasets.
- Other accessible sources that provide sufficient provenance.

Use official APIs, licensed datasets, RSS feeds, or permitted web extraction where appropriate. Respect source terms, access restrictions, robots policies, rate limits, and copyright requirements.

Do not assume that an LLM has live web access. Integrate a search or retrieval provider explicitly if live online discovery is required.

If external search is unavailable, the system must continue to work with its indexed knowledge base and clearly communicate the limitation.

### FR-4: Recipe knowledge base

Store recipe documents and their metadata in a searchable knowledge base.

Each record should support, where available:

- Source identifier and URL.
- Source title and author.
- Coffee name, producer, and estate.
- Country, region, varietal, and process.
- Roast information.
- Brewing method and equipment.
- Recipe parameters.
- Source publication or retrieval date.
- Extracted text and provenance.
- Embedding or retrieval representation.
- Extraction confidence and recipe completeness.

The system should support ingestion, deduplication, updating, and removal of stale or inaccessible records.

### FR-5: RAG retrieval

Implement a retrieval pipeline that combines semantic similarity with structured filtering.

Recommended approach:
1. Build a query from the resolved coffee identity and relevant metadata.
2. Retrieve candidate recipes using keyword search, vector search, or hybrid retrieval.
3. Rerank candidates according to coffee identity, brewing method, recipe completeness, and equipment compatibility.
4. Evaluate whether the evidence supports an exact match, a related match, or only general guidance.
5. Pass the best evidence to the recipe synthesis stage.
6. Preserve source references so every retrieved claim can be traced back to its origin.

The system should use configurable relevance thresholds rather than treating every vector-search result as relevant.

A low similarity score alone should not be the only reason to reject a result; identity, content, and recipe completeness must also be evaluated.

### FR-6: Recipe recommendation engine

- Generate actionable recipes using structured inputs.
- Prefer relevant source recipes when they exist.
- Adapt recipes to supported grinders and drippers.
- Fall back to a sensible baseline when retrieval fails.
- Validate arithmetic and recipe completeness.
- Explain important adaptations.
- Clearly label sourced recipes, adapted recipes, and generated recipes.

### FR-7: Equipment personalisation

- Allow users to select or save equipment profiles.
- Support optional grinder and dripper information.
- Maintain a configurable equipment catalogue.
- Use equipment-specific guidance only when sufficient information is available.
- Provide useful defaults when the equipment is unknown.

### FR-8: Recipe feedback and history

- Allow users to save a recipe and record brewing outcomes.
- Store the recipe version and parameters used for each brew.
- Suggest controlled adjustments based on feedback.
- Enable comparison between attempts.
- Use previous feedback when making subsequent recommendations, without overwriting the original recipe.

### FR-9: Explainability and provenance

For every recommendation, make it possible to determine:
- What was extracted from the coffee bag.
- What was obtained from external sources.
- Which retrieved sources influenced the recommendation.
- Which parameters were adapted.
- Which parameters were generated by the AI.
- Where uncertainty remains.

Every source citation must refer to an actual retrieved record or accessible URL. Never generate fictional citations or attribute an AI-generated recipe to a real brewer.

### FR-10: User experience

Create an intuitive, mobile-friendly interface with the following main screens:

1. Home screen with a prominent Scan Coffee Bag action.
2. Image capture and upload screen.
3. Extracted coffee profile and correction screen.
4. Optional equipment configuration screen.
5. Recipe discovery and evidence screen.
6. Recommended brewing recipe screen.
7. Brew feedback and history screen.

The recipe screen should prioritise usability during brewing. Use clear typography, metric units, readable timings, and a step-by-step layout.

## 6. Suggested Technical Architecture

Design the application using modular components so that the OCR model, LLM, vector database, and external search provider can be replaced independently.

A suggested architecture is:

**Frontend**
- Responsive web application or mobile-friendly progressive web app.
- Camera and image upload.
- Coffee profile editing.
- Equipment selection.
- Recipe display, saving, and feedback.

**Backend API**
- Image upload and processing.
- Coffee profile normalisation.
- Recipe search and retrieval orchestration.
- Recipe generation and validation.
- User preferences and brew history.

**Vision and extraction service**
- OCR and/or a vision-capable LLM.
- Structured extraction into a validated schema.
- Confidence handling and unknown values.

**Recipe ingestion pipeline**
- Source discovery.
- Content extraction.
- Recipe identification and parsing.
- Metadata enrichment.
- Deduplication and indexing.

**Retrieval service**
- Keyword or full-text search.
- Vector search.
- Hybrid retrieval and reranking.
- Source relevance evaluation.

**Recipe synthesis service**
- Evidence-grounded LLM prompts.
- Equipment-aware adaptation.
- Structured recipe output.
- Arithmetic and constraint validation.

**Data layer**
- Relational database for users, coffee profiles, equipment, recipes, and brewing history.
- Vector index for semantic retrieval.
- Object storage for uploaded images, if persistent image storage is required.

Use appropriate technologies based on project constraints rather than introducing unnecessary infrastructure.

A possible implementation stack is Python with FastAPI, a vision-capable LLM, PostgreSQL with pgvector, and a React-based frontend. These are suggested defaults, not mandatory requirements.

## 7. Suggested Recipe Data Schema

Represent recipes as structured data rather than relying exclusively on free-form LLM responses.

A recipe should include fields such as:

- `recipe_id`
- `coffee_identity`
- `source_type`: exact match, related coffee, curated baseline, or AI-generated
- `source_url`
- `source_title`
- `dripper`
- `grinder`
- `dose_g`
- `water_g`
- `ratio`
- `water_temperature_c`
- `grind_description`
- `bloom_water_g`
- `bloom_time_seconds`
- `pour_schedule`
- `target_brew_time_seconds`
- `instructions`
- `expected_flavour`
- `evidence_summary`
- `adaptations`
- `confidence`
- `limitations`

Each pouring stage should have its own water quantity, timing, and optional pouring instructions.

Use a schema validation library to ensure that model outputs conform to the expected structure. Validate the water totals, ratio, temperature range, and other important constraints before displaying the recipe.

## 8. Non-Functional Requirements

### Reliability
- Gracefully handle poor image quality, failed OCR, unavailable sources, and LLM errors.
- Never silently substitute invented facts for missing information.
- Ensure generated recipes pass basic consistency checks.

### Performance
- Provide useful progress indicators during image processing and retrieval.
- Cache reusable retrieval and metadata results when appropriate.
- Keep the architecture responsive even when external search providers are slow.

### Security and privacy
- Validate uploaded files and restrict accepted formats and sizes.
- Keep API keys and secrets on the backend.
- Use appropriate authentication and authorisation if accounts are implemented.
- Avoid retaining personal data or uploaded images longer than necessary.
- Apply reasonable request limits and input validation.
- Treat retrieved webpages and documents as untrusted content rather than instructions to the AI system.

### Maintainability
- Use modular components and typed interfaces.
- Keep prompts and model configurations versioned.
- Provide structured logs without unnecessarily exposing user data or secrets.
- Include automated tests, setup documentation, and clear environment configuration.

### Cost awareness
- Avoid unnecessary LLM calls.
- Use lightweight OCR or structured extraction where appropriate.
- Cache reusable embeddings and search results.
- Make model providers configurable.

## 9. Evaluation and Success Criteria

The project should be evaluated on both technical correctness and brewing usefulness.

**Image understanding**
- Accuracy of extracted coffee brand, estate, origin, process, roast, and tasting notes.
- Correct handling of fields that are absent or illegible.
- Rate of unsupported or hallucinated metadata.

**Retrieval quality**
- Precision of the top retrieved recipes.
- Ability to distinguish exact coffee matches from related coffees.
- Quality of source attribution and recipe completeness.
- Correct rejection of irrelevant search results.

**Recipe quality**
- Arithmetic correctness of dose, ratio, and water totals.
- Completeness of brewing instructions.
- Compatibility with the user's selected equipment.
- Quality of evidence-based adaptations.
- Usefulness of fallback recipes when no relevant evidence exists.

**Transparency**
- Percentage of sourced recommendations with valid provenance.
- Correct labelling of generated and adapted recipes.
- Clear communication of uncertainty and search limitations.

**User experience**
- Time from image upload to an actionable recipe.
- Ease of correcting extracted information.
- Ease of following the brewing instructions.
- Usefulness of feedback-driven recipe adjustments.

Create a test dataset containing coffee bags with different layouts, origins, roast levels, processing methods, and image quality. Include cases with exact matching recipes, only related recipes, incomplete source data, and no relevant recipes.

## 10. Important Edge Cases

The implementation must account for the following scenarios:

1. The coffee bag does not mention its roast level.
2. The roast date is present, but the roast level is not.
3. OCR confuses the estate name with the roaster's brand name.
4. Several different coffees have the same estate or product name.
5. A matching coffee exists, but the available online page contains no brewing recipe.
6. Retrieved recipes conflict on temperature, ratio, or grind size.
7. A retrieved recipe uses equipment the user does not own.
8. The user has an unknown or unsupported grinder model.
9. A source is inaccessible or its recipe cannot be verified.
10. The external search provider is unavailable.
11. The user uploads a photograph of a different product.
12. The retrieved content contains malicious instructions intended to influence the LLM.
13. The generated recipe contains inconsistent water quantities or impossible timing.
14. The system finds a related recipe but no exact match.
15. The user provides feedback that contradicts the initial flavour prediction.

The system should respond safely and transparently to each case.

## 11. Implementation Strategy

Build the application incrementally.

**Phase 1 — Functional MVP**
- Upload a coffee bag image.
- Extract and edit coffee metadata.
- Accept optional grinder and dripper preferences.
- Generate a baseline pour-over recipe.
- Validate recipe arithmetic.
- Display the recipe in a usable interface.

**Phase 2 — RAG-based recipe discovery**
- Ingest a small, curated set of real brewing recipes.
- Create the recipe knowledge base.
- Implement hybrid retrieval and relevance evaluation.
- Display actual source links and matching explanations.
- Distinguish exact matches, related recipes, and generated recommendations.

**Phase 3 — Online discovery**
- Integrate a permitted web search or source-specific ingestion mechanism.
- Retrieve newly discovered recipes.
- Extract and validate recipe parameters.
- Index relevant content for future queries.
- Track source provenance and retrieval dates.

**Phase 4 — Personalisation and iterative brewing**
- Expand grinder and dripper support.
- Add saved equipment profiles.
- Implement brew logging and recipe comparisons.
- Recommend targeted adjustments using feedback.

Prioritise a working end-to-end MVP before adding unnecessary infrastructure or advanced features.

## 13. Definition of Done

The project is considered complete when a user can:

1. Photograph a real coffee bag.
2. Review and correct the extracted coffee details.
3. Optionally select their grinder and dripper.
4. Retrieve relevant existing recipes from the configured knowledge sources.
5. See the original sources and understand how closely they match the coffee.
6. Receive a personalised recipe based on the evidence and equipment.
7. Receive a reasonable fallback recipe when no relevant recipe is found.
8. Follow the recipe using clear quantities, timings, and instructions.
9. Record the brewing outcome and receive a targeted recommendation for the next attempt.

The application must demonstrate a complete end-to-end workflow and must not rely on hardcoded example results to simulate OCR, RAG retrieval, or recipe generation.

## Final Product Vision

BrewWise should behave like a knowledgeable specialty coffee companion: it reads the bag, researches what other brewers have tried, understands the user's equipment, and recommends a practical recipe with evidence and reasoning.

Its defining feature is not simply generating a plausible coffee recipe. It is **connecting the identity of a specific coffee to real brewing knowledge, adapting that knowledge to the user's setup, and being transparent when the evidence is insufficient**.


### Mandatory Requirement: Live Web Discovery for Every Coffee Scan

The application must implement a dedicated online discovery and ingestion pipeline that searches the live web for existing brewing recipes whenever a user scans a coffee bag. Searching only a pre-populated vector database is not sufficient.

The pipeline must:

1. Build search queries from the extracted coffee metadata, prioritising the exact coffee name, roaster, estate, processing method, and relevant brewing terminology.
2. Search publicly accessible online sources using a configurable web search API or other permitted discovery mechanism.
3. Identify potentially relevant recipe pages, community discussions, blogs, and brewing guides.
4. Fetch accessible pages where permitted, extract their content, and identify actual pour-over recipes and their parameters.
5. Verify that each result contains useful brewing information and assess whether it refers to the exact coffee or a related coffee.
6. Normalise extracted recipes into a structured schema, preserving source URLs, titles, authors where available, retrieval timestamps, and provenance.
7. Deduplicate results and evaluate recipe completeness and relevance before using them.
8. Feed the newly discovered, validated recipes into the RAG retrieval and recommendation pipeline for the current request.
9. Optionally persist useful, permitted content in the knowledge base for future searches, subject to source access restrictions and applicable terms.
10. If live search fails, report that limitation and fall back to the existing knowledge base and a clearly labelled AI-generated recipe.

**Important implementation constraints:**
- Live discovery must run as part of the normal coffee-scanning workflow, not only as a manual administrative ingestion task.
- Do not assume that the LLM itself has internet access. Implement an explicit search integration and page-fetching mechanism.
- Do not treat search snippets as complete recipes. Fetch and inspect the underlying page when access is permitted.
- Do not fabricate recipes, URLs, authors, or claims that a recipe was found online.
- Preserve source attribution and distinguish exact matches from recipes for similar coffees.
- Use configurable timeouts, retry limits, rate limits, and caching to control latency and API costs.
- If a source blocks automated access, requires authentication, or prohibits extraction, respect those restrictions and use accessible alternatives.
- Make it possible to configure the search provider through environment variables without hardcoding API keys.

**Acceptance criterion:** Given a newly scanned coffee that has not been pre-indexed, the application must attempt a live web search using its extracted metadata, process accessible results, and use any relevant discovered recipes in its recommendation. If no relevant recipes are found, it must explicitly distinguish that outcome from a search failure and generate a fallback recipe.
